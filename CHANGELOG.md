# Changelog

All notable changes to mesa-core. The MESA specification documents carry their own version history.

## 1.3.0 - 2026-08-01

Implements MESA Specification 1.1.0, whose leading feature is the device inheritance scope. The profile format `schema_version` is now `1.1`. All format changes are additive: every valid 1.0 document remains valid. Deployments sharing a profile store across versions MUST upgrade readers before writing device-scoped profiles, because a 1.2.x reader rejects `inheritance_scope: device` at validation (loudly, per the new Spec 23 unknown-enum-value rule).

### Added

- **Device inheritance scope (Spec 5.6).** A fifth level, keyed by the HA device registry entry that owns an entity, ranked between entity and area: `get/set/delete_device_profile`, `device_keys()`, async variants, the `get_entity_device` host callback on `ProfileStore` and `InheritanceResolver`, and the `__device__:` reserved namespace. Without the callback there is no fallback and device profiles are inert. The Rule A and Rule B loosening overrides remain valid at entity scope only; a device profile tightens freely for every entity the device owns.
- **Capability hint resolution (Spec 4).** `capability_semantics.control_mode` on an integration-scoped profile now participates in Rule A as that profile's contribution when its `operational_boundaries.control_mode` is absent, attributed below every operational_boundaries declaration. The enum is validated in both the validator and the canonical JSON Schema; the rest of `capability_semantics` stays unmodelled. Previously the field was specified as the lowest precedence rung but implemented nowhere.
- **Query filters (Spec 9.2).** `query(devices=...)` and `query(integrations=...)`, and the matching `mesa_query_profiles` parameters. Each requires its host mapping callback and raises `ValueError` (surfaced as `invalid_query` over MCP) without it, mirroring `areas`; there is deliberately no domain fallback for the integrations filter, because a fallback filter would silently change which rows match.
- **`SemanticProfile.freshness()` and `FreshnessReport`,** exported from the package root: the status and the invalidation warnings from a single evaluation, for callers that want both.
- **Profile validity evaluation (Spec 5.5).** `SemanticProfile.validity_warnings(now=..., known_entity_ids=..., integration_version=..., ha_version=...)` evaluates the stored-but-previously-unread `profile_valid_for` triggers. Each check runs only when the host supplies its input; a declared `review_after_days` with no parseable anchor warns rather than staying silent; version pins compare as exact strings.
- **Scoped orphan detection.** `find_orphans` accepts `known_domains`/`known_integrations`/`known_areas`/`known_devices` registries and reports scoped orphans as their full reserved key; the plain one-argument call is unchanged.
- **Schema migration 1.0 to 1.1.** `migrate_profile` walks registered steps; the 1.1 step restamps only (the format is additive). A document without a `schema_version` is treated as 1.0-era and migrated, where it was previously read as already-current and skipped.
- **Portable archive `devices` section.** `format_version` is `1.1`; import accepts both `1.0` and `1.1`. Older mesa-core versions reject a 1.1 archive outright, which is the intended fail-closed behaviour: the alternative was silently dropping the devices section on import.

### Fixed (safety)

- **Service parameters could override the entity being enforced.** The documented handlers merged the caller's service data over the validated target (`{"entity_id": entity_id, **service_data}`), so a caller supplying its own `entity_id` replaced it. Policy was then selected for one entity while the executed call, and the confirmation challenge the operator approves, named another: a challenge could read `light.x` while its bound parameters targeted `lock.front_door`. Home Assistant's REST service API accepts `entity_id` inside the service data, which is exactly how such a parameter reaches the wire. The examples now merge the validated target last, and `MesaEnforcer.evaluate` no longer relies on them doing so: a `service_params` naming a different entity than the one being evaluated is denied outright as a contradictory target, audited, and never issued a challenge, because there is no safe way to guess which target the operator meant.
- **Invalidation was evaluated per request instead of per entity.** `get_validity_context` took no argument, so one `integration_version` was compared against every profile in a result set. A deployment runs many integrations at different versions, so a ZHA-pinned profile was checked against Hue's version and reported stale on the strength of a version it was never authored against. The callback now receives the entity ID and is called once per entity. It also now guarantees a single evaluation per entity: status and warnings previously came from two separate passes, so a one-shot iterable passed as `known_entity_ids` was consumed by the first and read as an empty registry by the second, making `mesa_get_profile` answer `current` with a false removal warning while `mesa_query_profiles` answered `stale` with none. `SemanticProfile.freshness()` returns both from one pass, and `known_entity_ids` is typed `Collection` rather than `Iterable`.
- **Host-supplied validity context was trusted without checking its types.** A `known_entity_ids` given as a bare string was iterated as a collection of characters, so every real entity read as removed and correct profiles were reported stale; a non-iterable raised out of the handler as `server_error`. Each recognised value is now type-checked and a wrong-typed one is dropped with a logged warning. An `async def` callback, which returns a coroutine that previously read as "not a dict" and silently disabled every invalidation check, is likewise refused with a warning. `known_entity_ids` must be a reusable collection: a one-shot iterable is refused, because the callback runs once per entity and the same generator handed back for each would be drained by the first row of a query, leaving later rows to read an empty registry and report existing entities as removed.
- **Entities profiled only by a scoped layer omitted `staleness_status`.** The check read the stored entity profile, so an entity resolved entirely from an inferred domain, integration, area, or device profile returned `metadata_origin.source: inferred_ai` with no staleness field, which Spec 9.3 requires whenever that origin is surfaced. It now reads the effective profile's origin.
- **Invalidation triggers never reached retrieval.** Spec 5.4 defines a profile as stale when its age has expired **or** an invalidation trigger has fired, and Spec 5.5 asks hosts to surface a warning when one fires. `profile_valid_for` was parsed, validated, and resolved, but nothing evaluated it on the MCP path, so a profile invalidated by an integration upgrade or a removed entity kept reporting `staleness_status: current` and an agent kept trusting it. `staleness_status()` now evaluates the triggers alongside age, `register_mesa_tools` accepts a `get_validity_context` callback supplying the deployment facts (`known_entity_ids`, `integration_version`, `ha_version`) that mesa-core cannot know on its own, and both retrieval tools surface fired triggers as warnings for profiles of every origin. `review_after_days` needs no host input and is evaluated either way; a trigger that cannot be evaluated is reported without changing the status.
- **Malformed Enrichment Section 11 fields silently lost lease protection.** `LeaseManager` read `cooperative_priority.level`, `trigger_entities`, `condition_entities`, and `affected_entities` raw: a typo'd level (`"protectedd"`), a non-object `cooperative_priority`, or a wrong-typed entity list dropped the automation from the conflict check entirely, granting leases the profile existed to deny, or crashed the request with `AttributeError`. Unrecognized levels and malformed priority objects now read as `protected`; a malformed entity list makes the scope unevaluable and covers every requested entity; every case surfaces a warning naming the automation and field.
- **The raw SDK adapter raised `KeyError` for unknown tool names.** Both `dispatch()` and the installed `call_tool` handler now return the Spec 9.6 `unknown_tool` error envelope, matching every other error path.

### Fixed (correctness)

- **Lease timestamps were timezone-naive.** Default clocks are now `datetime.now(UTC)`, so `expires_at` strings and audit/sensor timestamps carry an offset. Caller-supplied `now` values are used as-is.
- **`TriggerValidator.validate` re-walked every automation config per declared-none entity,** re-invoking the host's `expand_target` registry callback for each pair. Configs are now walked (and targets expanded) exactly once per call.

### Documentation

An audit of the 1.1 documents against the implementation found drift, most of it predating this release, all of it now corrected: the Overview promised that tool registration installs enforcement (it does not; enforcement lives on the host's service-call path), the custom MCP adapter example omitted the required `description` parameter, `TemporalEvaluator.apply()` was shown returning boundaries rather than a `TemporalResult`, the `SemanticProfile` and `ProfileStore` listings had drifted from the dataclass and the optional `get_deployment_defaults()` return, the Full Integration example omitted `get_entity_device` and `get_entity_integration` (leaving device scope inert for anyone following it) and showed no authentication gate, the semantic-moments callback did not explain the host-side transform from Home Assistant's separate trigger and condition arrays, the Getting Started install step omitted the `[fastmcp]`/`[mcp]` extra its own next snippet needs, and version metadata still read 1.2 across the specification, `SECURITY.md`, and the canonical schema. The specification now documents that `privacy_classification` is always present on query results and exempt from `include_fields`, and that query rows enumerate entities carrying their own profile. Two examples added in this cycle were wrong and are fixed: the device-scope camera profile used a `deny_response_mode` value that does not exist, and its closing prose overstated entity-level precedence against the most-restrictive privacy rule. A new test sweeps every fenced JSON and YAML example in `documents/` through the validator, so an invalid example now fails the suite.

A pass against Home Assistant's own documentation corrected the remaining integration guidance: the Getting Started enforcement example raised on every denial and so discarded the confirmation challenge, making `control_mode: confirm` impossible to implement from the docs, and mapped Level 1 conformance to the step that registers Level 3 retrieval tools; the Full Integration example's authentication gate raised from the caller-context callback, which the handlers answer with `server_error` rather than the `unauthorized` envelope, so it now gates at the transport; the custom adapter example annotated `ToolHandler` without importing it, which raises `NameError` on Python 3.11 through 3.13 where annotations are evaluated eagerly; the area callback now resolves the effective area (the entity's own, falling back to its device's) and the examples use bare HA area registry IDs rather than an invented `area.` prefix; and the validity-context example no longer implies every integration exposes a version, since Home Assistant requires `manifest.version` only for custom integrations. The specification now states that `review_after_days` counts from `last_updated` and needs it, that a trusted profile is reported as invalidated rather than stale, and how the documents are versioned relative to each other.

A further pass closed the remaining integration guidance. The Full Integration example's authentication gate used a `@app.middleware` decorator that exists on neither supported server (the MCP SDK's FastMCP takes a token verifier and auth settings at construction; standalone FastMCP registers middleware through `add_middleware`), and its service handler raised on every denial and accepted no confirmation token, so the nominally complete example made `control_mode: confirm` unimplementable just as the Getting Started one had. The Getting Started enforcement snippet passed neither the real service parameters nor a canonical `domain.service`, which silently skips every declared limit whose parameter is absent, and it now shows the resubmission call. The guide no longer presents its first three steps as Level 3 conformance, since they omit authentication, the resolver callbacks, caller context, and the filter set. `review_after_days` is a SHOULD rather than a MUST, matching what the validator actually enforces. The entity registry guidance now unions registry IDs with current state IDs, since neither alone is complete, and the Enrichment document states that releasing a terminated session's leases is a host responsibility the lease manager cannot perform for it.
A final pass corrected the Full Integration example itself, which readers copy wholesale. Its service tool took `**kwargs`, which standalone FastMCP refuses to register at all and the MCP SDK publishes as a required parameter of its own, so the service parameters that carry declared limits could not be supplied; it now takes an explicit `service_data` dict, and a test registers the documented signature against both servers and asserts the published schema, since a host's own tool function is otherwise never exercised by this suite. The example also constructed a plain, unauthenticated server while describing authentication only in a comment, so following it produced exactly the unauthenticated Level 3 server the specification forbids; the active constructor now builds an authenticated server, with a token verifier implementing the SDK's protocol, concrete URLs, the standalone FastMCP equivalent, and a note that this path secures an HTTP transport while `run()` defaults to stdio.


### Changed

- **The `mcp` and `fastmcp` extras carry upper bounds** (`mcp>=1.27,<2`, `fastmcp<4`). Both adapters target these frameworks' current major APIs, and the MCP SDK v2 rewrite moves the import paths they use, so an unbounded extra would install a release that breaks the adapters.
- **Python 3.12 is now the minimum.** 3.11 is dropped. The supported range is what the test suite can realistically cover, and the narrower floor also allows current syntax internally (PEP 695 type parameters).
- **`mesa_version` in MCP responses is `1.1`.** `ProfileMetadata.schema_version` defaults to `1.1` for programmatically built profiles; `from_dict` keeps `1.0` for stored documents that declare none (they are 1.0-era and are never silently migrated).
- **`component_type` is derived from the entity ID's domain** (`automation`, `scene`, `zone`, `person`, `helper`, else `entity`) instead of always `entity`. The spec enum was narrowed to the values a query can actually emit; results are always entity-keyed, so no scoped component type exists.
- **`explain` output can name the `device` level** in `provided_by_level` and competing values.

## 1.2.1 - 2026-07-12

A consolidated security and conformance release. Every finding below was reproduced against 1.2.0 before being fixed, and each carries a regression test. Operators running 1.2.0 or earlier SHOULD upgrade.

### Fixed (safety)

- **The built-in domain safety baseline applied to profiled entities.** It is scoped to entities with no profile at any inheritance level (Spec 5.8); it was applied whenever no layer happened to declare `control_mode`. A `light` profile carrying only tags therefore resolved to `autonomous` rather than the mandatory `confirm` default (Spec 4), and did so for `inferred_ai` profiles too, violating inferred Rule 8. A profiled entity that leaves `control_mode` undeclared now defaults to `confirm`, and a deployment default may not loosen an entity whose profiles are all of untrusted origin.
- **An `inferred_ai` profile could self-confirm its own fields.** `confirmed_fields` was honoured from any origin, so an inferred profile listing `operational_boundaries.control_mode` escaped Rules 8 and 9 silently: an inferred `lock` profile could assert `autonomous` and an inferred helper could assert `triggers_automations: none`. Confirmation promotes fields to `hybrid` (Rule 6), so `confirmed_fields` is now honoured only from `hybrid`, and is rejected at validation on any other origin.
- **Unconfirmed `hybrid` fields were treated as trusted.** Unconfirmed fields remain inferred (Rule 6), but Rule D placed every `hybrid` field in the trusted tier, letting an unconfirmed entity-scope `declared_limit` displace a developer-declared cap of the same `id`. Rule D and the limit/temporal union now compute trust per field.
- **`declared_limit` predicates were disabled by unavailable entities.** Only a `None` state was treated as unevaluable, so HA's `unavailable` and `unknown` state strings compared cleanly to False and dropped the limit (Spec 6.5 names both as unevaluable). A `get_state` callback that raises is likewise treated as an evaluation failure rather than escaping the enforcement path.
- **A malformed `deny_for` disabled privacy denial.** `access_roles` contents were unvalidated, so `"deny_for": "guest"` was read as a set of its characters: it denied nobody named `guest`, and denied anyone named `g`. `access_roles` is now validated in both the validator and the JSON Schema.
- **Retrieval never applied `access_roles` or `deny_response_mode`.** A conforming implementation with caller context MUST apply `access_roles` before acting on or surfacing data (Spec 7.2); `mesa_get_profile`, `mesa_query_profiles`, and `mesa_explain_profile` applied it to neither, so an authenticated caller listed in `deny_for` received restricted profiles in full. All three now shape responses per `deny_response_mode` (`omit`, `redact`, `error`), which previously had no consumer anywhere. This also closes an audit gap: access to a restricted or person entity is now logged on retrieval, not only on service calls (Spec 7.1, 17).
- **An invalid server `mode` failed open.** Any string other than `"enforced"` read as advisory, so `mode="enfroced"` silently downgraded enforcement deployment-wide. Rejected at construction.
- **Malformed temporal constraints validated and were then ignored.** Only the condition type and the presence of an effect were checked. Type-specific required fields, weekday and solar-event vocabularies, and the effect cross-field rules are now validated, so an effect that constrains nothing, or a `day_of_week` naming `saturday` instead of `sat`, is rejected at authoring time instead of silently disabling the restriction. An unrecognisable day list is now unevaluable and therefore active, and a non-string `start_time` no longer raises `TypeError` out of `evaluate()`.
- **A lint-clean profile could disable the whole store.** `validate_document` coerced a non-object `semantic_profile` to `{}` and reported the document clean; `from_dict` then raised `AttributeError`, which is not a `MesaValidationError` and so escaped every guard, taking down `store.get`, `get_effective`, and whole-store `query` scans. Rejected in the validator now.
- **Portable import could write through reserved namespaces.** Archive keys were unvalidated, so an `entities` entry named `__domain__:lock` was written as a domain-wide policy. Reserved keys are quarantined, malformed sections and non-object deployment defaults are reported in `ImportResult.invalid` instead of raising `AttributeError` or being silently dropped.
- **`DeploymentDefaults` accepted malformed nested overrides.** They are read only for entities with no profile at any level, so a bad `domain_overrides` value sat inert until the one case it exists to cover and then crashed resolution with a raw `ValueError`/`TypeError`, or silently returned the wrong policy (`"control_mode" in override` is a substring test on a string). Validated at parse, raising `MesaValidationError`.
- **Lease state was not synchronised.** `arequest` offloads to threads, and granting is a check-then-act, so concurrent requests double-granted the same entity and `active_leases()`/`sensor_state()` could raise `RuntimeError: dictionary changed size during iteration`. Lease lifecycle operations now hold a reentrant lock.
- **A same-session lease "refresh" created overlapping leases.** The old lease was never removed, so a keep-alive doubled `active_lease_count`, published the superseded lease's expiry as `earliest_expiry`, and fired `mesa_lease_expired` for an entity the session still held, telling native automations to resume mid-operation. A refresh now supersedes the prior hold with no event, because the hold is continuous.
- **A raising host callback abandoned lease releases.** An `on_lease_event` that raised during `release_session` left the remaining leases of a terminated session held, against Spec 21.4, and permanently lost expiry events. Callback failures are logged and isolated. A raising `get_state` in the protected-automation check is treated as active (fail-closed), matching the existing `None` handling.
- **`TriggerValidator` only saw entity-level declarations.** Agents consume the effective profile, so a `none` inherited from a domain, integration, or area profile, or from a deployment default, skipped the check entirely. It now resolves. `validate()` accepts an optional `entity_ids` registry, without which entities inheriting `none` and carrying no stored profile of their own cannot be enumerated.
- **A malformed `declared_limits` silently dropped every limit in it.** The validator and the parser both read the field with `or []`, so a `declared_limits` given as an object, `0`, or `""` was read as "no limits declared" rather than as malformed, and the entity kept none of its safety limits. Found while driving the validator and the canonical schema to agreement, not reported by the audit. Both fields are now checked for being arrays, which also stops a truthy scalar raising `TypeError` out of the validator.
- **`confidence: true` read as full confidence.** `isinstance(True, int)` is True and `float(True)` is 1.0, so a boolean confidence on an `inferred_ai` profile passed the 0.0-1.0 check and then cleared the Rule 3 threshold as 1.0. Rejected now. Also found during the agreement work.
- **The validator raised instead of reporting on hostile input.** An unhashable predicate operator, condition type, or weekday reached a set or dict membership test and raised `TypeError`, so `from_dict` failed with `TypeError` rather than `MesaValidationError` and escaped every caller's guard.

### Fixed (correctness)

- **The FastMCP adapter published the wrong input schema.** It registered a single `params: dict` argument and discarded the schema it was handed, so the published `inputSchema` was `{"params": {...}}` and every payload documented in Spec 9.5 was rejected. Since FastMCP derives the schema by introspecting the function, the registered function's signature is now built from the tool's declared schema on both lineages (`fastmcp` and `mcp.server.fastmcp`), which also restores enforcement of the declared constraints. Tests now assert the published schema and issue real documented calls.
- **Effective profiles dropped enrichment and vendor fields.** Resolution built a fresh profile, so `helper_traits`, `semantic_routing`, spatial and automation semantics, and vendor extensions vanished from `get_effective()` and `mesa_get_profile`, contradicting both "complete effective profile" retrieval and forward compatibility (Spec 23). Unmodelled fields are now carried across resolution and resolved per leaf path under Rule D and Rule E (see the enrichment-trust and nested-field entries below), so a complete effective profile stays complete.
- **Edits to a parsed profile were silently discarded.** `to_dict()` returned the original document whenever one existed, so the natural read-modify-write (`get`, tighten `control_mode`, `set`) persisted the old value with no error. `to_dict()` now serialises the typed fields and merges the unmodelled entries of the source document back around them.
- **Programmatically built profiles serialised defaults as declarations,** which changes Rule E inheritance on reload. A field is now serialised only when the source document declared it or it has been set away from its default; `SemanticProfile.declared_paths` records the former.
- **Diagnostic profile selection ordered scope before trust,** letting an untrusted entity-scope diagnostic profile displace a trusted broader one. It now follows Rule D: trusted tier, then scope, then origin authority.
- **Query cursors fingerprinted only entity keys,** despite the code claiming profile changes invalidate them. Content is now covered, so an edit that changes what a filter matches invalidates the cursor rather than silently reshuffling a page.
- **Confirmation approvals were not audited.** Spec 6.6 promises an audit trail carrying `approved_by` and `approved_at`; both reached only an in-memory warning string, and the allowed call was logged at DEBUG, so at a host's default level an approved door unlock left no record. A confirmed write is now always audited with the approval attached. (A token carrying no `approved_by`/`approved_at` is rejected outright, see the second remediation pass below.)
- **Expired confirmation challenges accumulated for the life of the process.** Redemption was the only removal path, and an unconfirmed call is never redeemed. `issue()` now evicts expired challenges.
- **An invalid-JSON integration sidecar raised `JSONDecodeError`** despite the documented contract promising `MesaValidationError`. Hosts running the documented startup recipe across installed integrations took an uncaught crash on one third party's typo.
- **The canonical JSON Schema and the runtime validator disagreed.** The validator accepted documents the schema rejected (a string `semantic_profile`, `control_mode: null`, a string `reversible`, person arrays given as strings) and the schema omitted most normative validation: enrichment objects, privacy booleans, role-array contents, temporal required fields, limit numeric types, and hybrid `confirmed_fields`. Both sides now agree, checked by a committed, seed-deterministic differential test (`tests/test_validation_schema_agreement.py`) that mutates rich base documents plus every valid fixture and asserts identical verdicts, alongside explicit regression cases and adversarial fixtures rather than the happy path alone. The schema also judges a bare `semantic_profile` body, which parsers accept: previously such a document matched nothing at the root and passed vacuously, so a third party validating with the canonical artifact would accept what mesa-core rejects.
- **MCP handlers coerced inputs with `bool()` and `int()`.** `bool("false")` is True, so a string `"false"` enabled `include_inferred`, defeating a gate the spec makes opt-in. Parameters are parsed strictly, and the tool schemas now set `additionalProperties: false` so a typo'd filter is an `invalid_query` rather than a silently unfiltered result set.
- **Unconfirmed inferred privacy could relax a trusted policy.** Rule D placed an untrusted access-control field in a lower tier but still selected it when no trusted layer declared one, so an inferred `access_roles.unrestricted_for: [guest]` relaxed a developer-declared restricted entity for a guest. The access-decision fields (`access_roles`, `is_minor`) are now excluded from the resolution entirely when only an untrusted layer declares them (Spec 5.4 Rule 3, Spec 17): they keep their safe default rather than take the inferred value. Informational privacy fields (the `contains_*` flags, etc.) keep the normal Rule D resolution, since an inferred value there only ever adds caution and never gates access.
- **A deployment default could loosen a profiled entity.** `deployment_defaults` are for unprofiled entities; a profiled one loosens only via the Rule A override (Spec 4 control_mode precedence, Spec 5.8). The fix applied the default whenever any human-authored layer existed, so a profiled entity with no `control_mode` took an autonomous deployment default instead of `confirm`. Deployment defaults now apply only when the entity has no profile at any level; a profiled entity that omits `control_mode` defaults to `confirm`.
- **An inferred helper could still resolve to `triggers_automations: none`.** The same deployment-default over-application let a `domain_overrides` entry drop a profiled inferred helper to `none`, violating Rule 9. A profiled entity's undeclared `triggers_automations` now takes the built-in baseline (helpers default to `likely`), never a deployment override.
- **An approval-less confirmation token was accepted.** `redeem` checked only `challenge_id` and the request binding, so a token carrying no `approved_by`/`approved_at` was accepted and produced no audit trail, defeating the protocol's stated purpose (Spec 6.6). The token schema records the approval, so both fields are now required and a token missing them is rejected.
- **Enrichment merge bypassed Rule D trust.** Unmodelled fields were carried onto the effective profile by scope alone, so a more-specific inferred profile overwrote developer enrichment. The carry now applies the Rule D order (trusted tier first, then scope), so an inferred entity cannot displace a developer domain's `helper_traits` or vendor fields.
- **Query pagination was inconsistent after access shaping.** `pagination.returned` reflected the pre-access page, so a denied row left `returned: 1` with an empty `results`. `returned` now equals the actual results length, and the handler documents that `total_matched` counts filter matches before per-caller shaping.
- **The `mcp.server.fastmcp` lineage and raw/custom dispatch were unverified.** MCP tool inputs are now validated against the declared schema at the handler boundary, the one funnel every transport and custom registry shares, so unknown fields, wrong types, and out-of-range values are rejected with `invalid_query` regardless of transport. Integration tests now exercise both the `fastmcp` package and `mcp.server.fastmcp`, asserting documented payloads work and adversarial ones are rejected. (The FastMCP adapter's coercion of string scalars, e.g. accepting `"50"` for an `integer`, was tightened to strict rejection in the second remediation pass below, so advertised and enforced match.)
- **The cursor fingerprint ignored inherited layers.** It hashed only entity documents, so a domain, integration, area, or deployment-defaults change could move a row across the page boundary without invalidating the cursor. It now covers every stored key.
- **The intent filter read stored routing instead of effective.** `intent_tags` inherited from a domain profile are exposed by `get_effective()` but were not matched by `mesa_query_profiles(intents=...)`; the filter now reads the effective profile.
- **A read-modify-write could poison the store.** `set` serialised without validating, so mutating a profile to an invalid state (e.g. changing the source to `inferred_ai` without confidence/generated_at) wrote a document the next `get` could not load. Setters now validate before committing and raise rather than write.
- **Validator gaps closed:** `profile_valid_for` and `diagnostic_profile` are validated as objects; `time_range` bounds must be 24-hour `HH:MM` (`"25:99"`, `"noon"`, `"12:00:00"` are rejected); `import_profiles` reports a non-object archive and non-object sections instead of raising `AttributeError` or silently accepting a falsy section; `DeploymentDefaults.from_dict` rejects falsy wrong-typed `triggers_automations_domains`/`domain_overrides`.
- **Unconfirmed hybrid enrichment could still override trusted enrichment.** The per-field hybrid-trust fix covered modelled Rule D fields but the unmodelled-field carry still ordered whole profiles by `is_trusted()`, so a hybrid layer that confirmed only `semantic_tags` overwrote a developer vendor field. The enrichment carry now resolves each field under Rule D per its `confirmed_fields` path, so an unconfirmed hybrid or inferred field cannot displace a trusted one, while an enrichment field with no trusted competitor is still carried.
- **Nested enrichment resolved atomically, breaking Rule E.** The carry treated a vendor object such as `helper_traits` as one value, so a developer `helper_traits.note` plus an inferred-only `helper_traits.new_hint` dropped the disjoint subfield, and a hybrid confirmation of `helper_traits.note` was not recognised. Dict-valued enrichment is now traversed to leaf paths (arrays and scalars stay atomic), so disjoint inherited subfields compose and a sub-path can be confirmed. Where layers disagree on shape (a scalar at one level, an object at another, or an empty object), which shape wins is itself a Rule D decision taken over the trusted tier first, so a broader inferred scalar can no longer overwrite a trusted entity object that shares its path prefix, a lower-tier scalar or empty object cannot force two trusted objects to resolve atomically and erase their disjoint subfields, and the result does not depend on layer iteration order. A hybrid layer keeps the node an object only when a confirmed path resolves to a field the object actually contains (a confirmation naming a nonexistent or stale descendant confirms nothing and cannot promote unconfirmed fields past a trusted declaration), and when an object beats a trusted atomic declaration this way, the trusted declaration remains a competitor for every child: unconfirmed siblings of the confirmed field are discarded rather than carried, so they cannot piggyback past it. A confirmed path covers the whole value declared at it: confirming `x_vendor.a` confirms everything under it, so a confirmed object-valued field keeps its contents through recursive composition instead of its children resolving as unconfirmed descendant paths and being discarded. A trusted, more specific atomic declaration still overrides a broader trusted object, and the losing shape is reported as a conflict.
- **A non-finite numeric bound disabled its limit.** `NaN`/`Infinity` are Python floats and `json.loads` accepts the non-standard tokens, so a `max_value: NaN` validated clean and then let an over-limit call through, because every comparison with `NaN` is false. Non-finite numbers are now rejected at validation (a `NaN` staleness window also no longer raises at parse). Standard JSON forbids them, so a conformant third-party parser never produces one; the check is a defense for Python callers and hand-edited stores. As defense in depth, the enforcer's limit comparison now fails closed on a non-finite bound (blocking rather than silently disabling the cap) instead of relying on validation alone.
- **An oversized JSON integer crashed validation and enforcement.** A valid but arbitrarily large integer (say 1,000 digits) was passed to `math.isfinite`, which converts to float and raises `OverflowError`, so `validate_document` and `mesa-lint` crashed on hostile input instead of returning a result, and the enforcer's `float(value)` limit comparison and the predicate helper `_compare` raised the same. A Python integer is always finite, so it is now accepted as a number without float conversion, and both enforcement paths catch the overflow and fail closed (an incomparable limit blocks; an unevaluable predicate is treated as active, keeping its limit enforced) rather than crashing. The same overflow was then closed at every remaining conversion site: an out-of-range oversized `confidence` is a normal validation error, `staleness_status()` compares in plain seconds instead of building a `timedelta` (an astronomically large window is simply never stale), an oversized `solar_offset_minutes` leaves its temporal condition unevaluable and therefore active, and an oversized lease `duration_seconds` is clamped to the 30s maximum as the published schema promises instead of returning `server_error`.
- **A non-finite state string disabled a numeric predicate.** `float("nan")` and `float("inf")` succeed, so a host `get_state` returning `"nan"` made every numeric comparison false and the predicate read as inactive, dropping its declared limit and allowing an over-limit call (Spec 6.5 requires unevaluable to fail closed). Numeric predicate operands now go through the finite-number helper, so a non-finite state or value is unevaluable and the limit stays active.
- **`profile_valid_for` bypassed Rule D and Rule E.** Effective metadata was copied wholesale from the most-specific layer, so a domain-level invalidation trigger vanished when a more-specific profile omitted it, and an unconfirmed hybrid value could overwrite a trusted one. `profile_valid_for` is now resolved per subfield (trusted tier, then scope) while the rest of metadata stays most-specific provenance, so a domain `integration_version` composes with an entity `review_after_days`, a hybrid can confirm a single subfield (`profile_valid_for.review_after_days`), and each resolved subfield carries its own explanation. Its four known members (Spec 5.5) are now typed in the validator and the JSON Schema, so a non-string `integration_version` or a non-finite `review_after_days` is rejected while unknown members stay forward-compatible.
- **`mesa_explain_profile` did not explain every effective field.** Only the kernel paths carried a `FieldExplanation`; `semantic_tags`, `diagnostic_profile`, `profile_valid_for`, and enrichment fields were in the effective profile with no entry, against Spec 9.5. Every effective field now has an explanation, and those explanations carry accurate conflict metadata: a `semantic_tags` union contributed by disagreeing levels, competing `diagnostic_profile` declarations, and competing enrichment leaves now set `conflict`, `conflict_resolution`, and `competing_values`, so `conflicts_detected` is no longer falsely `false` when several levels competed. `conflict` consistently means the levels declared differing values; identical declarations at several levels agree and are not reported (Spec 9.5's wording, which could be read either way, is clarified by an erratum in the same safe-diagnostics direction).
- **Published lease schemas were looser than enforced.** The strict `number` union emitted Pydantic's `gt`/`ge`/`le` (which JSON Schema validators ignore) rather than `exclusiveMinimum`/`minimum`/`maximum`, so a standards-compliant client was shown no bound on lease duration or caller priority even though the transport enforced one. Numeric constraints are now applied per union branch so the correct JSON Schema keywords are published, and the lease tools' published schema and transport enforcement are covered by integration tests.
- **A malformed deployment-defaults object aborted portable import.** `DeploymentDefaults.from_dict` now raises `MesaValidationError`, which `import_profiles` did not catch, so an archive with an invalid `default_control_mode` or nested override raised instead of being quarantined in `ImportResult.invalid`. Caught now.
- **Explicit JSON `null` bypassed input validation.** The MCP handler treated `null` on any optional parameter as "omitted," so a direct or custom-registry caller could send `{"domains": null}` (accepted, unfiltered) or `{"limit": null}` (reached `min(None, 200)` and returned `server_error`), contradicting the published schema. Explicit `null` is now a wrong-type error wherever the schema names a type, in MCP parameters and in portability archive sections; the FastMCP adapter strips its own injected `None` defaults so an omitted optional still works.
- **The FastMCP transport coerced schema-invalid scalars.** The adapter used plain `bool`/`int` annotations, so `mcp.server.fastmcp` accepted `{"include_inferred": "false"}` and `{"limit": "50"}` although its published schema said `boolean`/`integer`. The annotations are now strict, so a JSON string is rejected on both lineages and advertised equals enforced. (This is a contract fix, not a fail-open: `"false"` coerced to `False`, the leaking direction never occurred.) The integration test that blessed the coercion now asserts rejection.
- **Write validation ran after fallible serialization.** Assigning a malformed value to a typed field (e.g. `control_mode = "bogus"`) raised a raw `AttributeError` from `to_dict()` before validation. The write boundary now turns a serialization failure into `MesaValidationError`, for both profiles and `DeploymentDefaults`.
- **A mutated `DeploymentDefaults` was not revalidated on write.** `set_deployment_defaults` validated a dict input but trusted an already-constructed dataclass, so mutating `domain_overrides` to an invalid shape wrote clean and failed later at resolution. It is now revalidated regardless of input type.
- **`staleness_window_days` was silently truncated.** The specification and the JSON Schema declare a `number`, but parsing applied `int()`, so a valid `0.9`-day window round-tripped as `0` and marked a half-day-old profile stale. The declared value (int or float) is now preserved end to end, and the Module Proposal's dataclass listing matches the spec's `number`. Relatedly, `staleness_status()` no longer raises `TypeError` when a timezone-naive `generated_at` meets an aware `now`: when only one side carries a timezone, wall clocks are compared.
- **Merged effective profiles aliased their input layers.** Resolution installed several winning values by reference (Rule D winners such as `access_roles` and person arrays, deduplicated `declared_limits` entries, `diagnostic_profile`, and, when `profile_valid_for` needed no change, the source layer's entire metadata object including its `confirmed_fields` list), so a read-modify-write of a `merge()` or `get_effective()` result silently mutated the stored source profile. Resolved mutable values and explanation payloads are now deep-copied at the resolution boundary; the effective profile owns everything it holds.
- **Identical objects with different key order were reported as conflicts.** The Rule D distinct-values check used `repr()`, which preserves dict insertion order, so two semantically equal `access_roles` mappings produced `conflict: true` with populated `competing_values`, against the Spec 9.5 erratum. The check now uses the order-insensitive canonical serialisation the other resolvers already use. The canonical serialisation is also numerically value-semantic: JSON has one number type, so `1` and `1.0` (or `0` and `-0.0`) are the same declaration, not a conflict. A finite integral float normalises to the exact integer (never the other way around, which would falsely merge distinct integers beyond 2**53), and booleans remain a distinct type. The comparison is also field-aware where a field's consumer defines set semantics: the role arrays inside `access_roles` are read as sets by the privacy enforcer, so reordered or duplicated role lists are the same declaration, not a conflict (arrays elsewhere stay order-sensitive, and the effective value is never rewritten, only the comparison).
- **Dot-notation field paths were ambiguous.** A literal property name containing a dot renders identically to a nested path (`{"a.b": 1}` versus `{"a": {"b": 2}}`), so resolution emitted two explanations with the same `field_path`, and, worse, a `confirmed_fields` entry intended for a nested path also granted hybrid trust to the same-rendering literal key, letting that value displace a trusted declaration. The specification now defines the path grammar (Section 5.7, Field paths): a path always parses as dot-separated segments, a confirmed path covers the whole value beneath it, and a property name containing a dot (or backslash) is not path-addressable. It can never be individually confirmed (though a confirmed ancestor still covers it, and developer/user trust is unaffected since it does not derive from paths), and explanations render it escaped (`x_vendor.a\.b`) so reported paths stay unique. The grammar is applied everywhere subfield paths are built. Every field the specification defines is dot-free and unaffected.

## 1.2.0 - 2026-07-03

### Added

- **Portable profile export/import.** `export_profiles(store)` produces a single JSON archive of every stored profile document (entities, domain/integration/area scopes, deployment defaults); `import_profiles(store, archive, on_conflict=...)` restores it into any store with `skip`, `overwrite`, or all-or-nothing `error` conflict handling. Export is faithful (raw documents, nothing dropped); import validates every document and quarantines failures in `ImportResult.invalid`. Because the archive carries canonical profile JSON, it is storage-backend-agnostic: an export from one MESA-integrated host imports into any other, regardless of how either stores profiles internally. Async variants included.
- **Semantic moments (HA 2026.7+ purpose-specific triggers).** `mesa_get_profile` accepts `include_semantic_moments` and, when the host supplies the new `get_semantic_moments` callback, returns the purpose-specific triggers and conditions the entity participates in. Consumed live from HA at request time, never stored in profiles (so it cannot go stale), never consulted by enforcement, and documented as carrying no MESA authority beyond the integration that defined the moment.
- **`solar_angle` temporal conditions.** Evaluated through the new `get_solar_elevation(at)` host callback (in Home Assistant, the `sun.sun` entity's `elevation` attribute); mesa-core computes no astronomy. Each `solar_event` is an elevation-boundary crossing (`sunset` below 0 degrees, civil/nautical twilight at -6/-12), and `solar_offset_minutes` shifts the transition by sampling elevation in the past. Without the callback the condition stays fail-closed exactly as in 1.1, so existing profiles only gain evaluation, never lose protection. `MesaEnforcer` accepts and passes the callback through.
### Changed

- Specification 6.5 now states the `solar_angle` truth semantics explicitly (previously the fields were listed without defining when the condition is true).
- Documentation corrections: the version-scope ledger now says four inheritance levels (integration scope included), the Level 3 lease conformance row no longer defers to a future revision, profile editing UIs are documented as host-server territory rather than a MESA deliverable, and the architecture diagram is vendor-neutral.

### Related

- The `mesa-lint` CLI (0.1.0) shipped in this cycle as a separate package for CI validation of `mesa_profile.json` sidecars and profile stores.

## 1.1.0 - 2026-07-02

mesa-core 1.1 completes MESA Level 3: the advisory lease protocol and the standard audit event schema join the retrieval API, enforcement, and the confirmation protocol. It also closes every API gap reported by integrators since the 1.0.0 release.

### Added

- **Advisory lease protocol** (Enrichment Section 21). `LeaseManager` with request, early release, session release, and automatic (lazy) expiry; partial grants; the 30-second duration cap; `mesa_lease_expired` events through the `on_lease_event` callback; and `sensor_state()` for hosts exposing `binary_sensor.mesa_lease_active`. Lease requests for entities under `protected` or `critical` automation control are denied fail-closed. The `mesa_request_lease` and `mesa_release_lease` MCP tools register when `register_mesa_tools` receives a `lease_manager`. Scope is single-agent: overlapping requests resolve existing-holder-wins, and multi-agent priority preemption (Enrichment 21.6) is planned for v2.
- **Standard audit event schema.** Every record on the `mesa_core.audit` logger now carries a `mesa_audit_event` dict: `timestamp`, `caller_id`, `roles`, `entity_id`, `action`, `decision`, `profile_version`, `rule_applied`, `redaction_mode`, plus `event_type` and a `details` object. Emitted by `PrivacyEnforcer` (privacy access), `MesaEnforcer` (every blocked call at INFO; allowed calls at DEBUG), and `LeaseManager` (requests and lease endings). `MesaAuditEvent` and `emit_audit_event` are exported for hosts emitting their own events into the same stream.
- **Typed person traits.** `PersonTraits` (Enrichment Section 17) on `SemanticProfile`, resolved per-field under conflict Rule D. Fixes a privacy-enforcement gap: `is_minor: true` declared at domain or area scope now reaches enforcement instead of being read from the entity document only.
- **person_traits validation.** `household_role` is checked against the Section 17 enum and `is_minor` must be a boolean, in both the validator and the canonical JSON Schema.
- **Indirect automation references.** `TriggerValidator` and `entities_by_role` accept an `expand_target(kind, ref)` callback resolving `area_id`, `floor_id`, `label_id`, and `device_id` selectors to entity IDs, so stale `triggers_automations: none` declarations behind device triggers or the target blocks of purpose-specific triggers (Home Assistant 2026.7+) are caught. Without the callback, behaviour is unchanged.
- **ProfileStore async parity.** Async variants for domain-, integration-, and area-scope profile get/set, deployment defaults, and key enumeration, plus `explain()` and `aexplain()` delegating to the resolver. `TriggerValidator` gains `avalidate()` and `avalidate_entity()`. Async resolution goes through the store wrappers; `PrivacyEnforcer.evaluate()` stays synchronous-only as pure computation.

### Changed

- Enrichment Section 17: `household_role` relaxed from REQUIRED to RECOMMENDED, so the minimal safety-first declaration (`{"is_minor": true}`) is valid.
- Specification 5.5: hosts SHOULD expand target selectors to entities when cross-referencing automations, since raw configuration scanning sees only explicit `entity_id` references.
- Specification 7.1: the `mesa_audit_event` schema is the RECOMMENDED audit shape; the logging obligation itself remains format-flexible for third-party implementations.

### Compatibility notes

- Profiles with an invalid `household_role` or a non-boolean `is_minor` now fail validation at read; they were accepted by 1.0.0. Correctly declared profiles are unaffected. The non-boolean `is_minor` rejection is deliberate: such a value would otherwise silently disable the mandatory restricted behaviour.
- Audit log records replace the ad-hoc `mesa_*` extras of 1.0.0 (`mesa_decision`, `mesa_is_person`, and friends) with the single `mesa_audit_event` dict. Consumers parsing the old extras need a one-line change.
- `register_mesa_tools(lease_manager=...)` now registers the lease tools; in 1.0.0 the parameter was accepted and ignored with a warning.
